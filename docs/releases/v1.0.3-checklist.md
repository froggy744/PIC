# PIC v1.0.3 release checklist

Focus this release on performance, photographic quality, and reliability; defer large features.

## Performance targets

| Operation | Initial target |
| --- | --- |
| Thumbnail scrolling | No sustained frame stalls in normal browsing |
| Cached photo navigation | Under 100 ms where practical |
| Warm Edit Mode preview | Under 250 ms for common GPU adjustments |
| Repeated library opening | Avoid full rescans of unchanged files |

- [ ] Establish a baseline for each target before changing its implementation.
- [ ] Record hardware, library size, image formats and sizes, cache state, and measurement method with each result.
- [ ] Measure representative small and large libraries, including RAW photos.
- [ ] Use existing opt-in tracing to locate bottlenecks; record results after relevant changes.
- [ ] Check scrolling responsiveness during normal browsing.
- [ ] Measure cached navigation from user action to displayed photo.
- [ ] Measure warm Edit Mode adjustments from user action to updated preview, identifying the adjustments and GPU used.
- [ ] Measure repeated library opening, distinguishing enumeration and fingerprint checks from rereading metadata or regenerating thumbnails. The existing scanner already skips healthy records with matching fingerprints, but enumerates files; verify the relevant scan paths before changing them.
- [ ] Verify that additions, modifications, moves, and removals are still detected when optimizing reopening.

Current evidence: the local scanner enumerates the tree on an authorized scan and skips healthy records with matching modification time and size. The existing matching-fingerprint regression test passes. Scan authorization tests also pass for availability updates, programmatic selection, and debounced watch refreshes. These tests do not measure startup time or prove that every reopening path avoids scanning; the performance target remains open.

### Startup investigation (2026-11-06)

- Startup selects the registry's current catalog and opens SQLite on the main thread. Window construction reads folders, albums, counts, settings and the initial photo list before presentation. Gallery population starts on idle after presentation; availability checks and thumbnail recovery also run separately. A previously authorized unfinished network import may resume. Library switching opens the selected database and reloads the catalog on the main thread.
- `PIC_STARTUP_TRACE` now records startup catalog and photo-query durations and library-switch open, query and completion timings. Timing is opt-in and does not alter scan authorization.
- Isolated Xvfb/X11, Cairo, debug-profile binary, AMD Ryzen 5 5600G: a SQLite backup of an existing 8,756-photo catalog (364 folders, 9 albums; 8,745 local paths and 11 network URIs) was placed on `/tmp` (tmpfs), with isolated XDG state. These are process launches with OS caches uncontrolled, not cold-storage measurements; no live library database was opened by PIC. First paint does not prove thumbnails are visible.
- First launch: database open 6 ms, initial photo query 28 ms, first paint 583 ms. Gallery population started at 586 ms but had not returned from scheduling when the process was stopped at 12 seconds. The user reports that the initial delay involved unmounted drives; the exact blocking operation remains unconfirmed by these traces.
- Reopening the same isolated catalog: photo query 28 ms, first paint 592 ms, gallery population scheduled in 3 ms and restoration completed at 799 ms. A further run with a fresh thumbnail cache reached first paint at 596 ms and restoration at 759 ms. This does not reproduce the first launch delay; do not infer its cause.
- Remaining: reproduce and diagnose the first-launch delay; measure true cold storage, visible thumbnails, switching libraries, and local disk rather than tmpfs. No NFS mount was available. Obtain before/after measurements if a confirmed bottleneck is fixed. The catalog includes network URIs, so it is not a pure local-source workload.
- Verification: `cargo check --locked` and the isolated startup GUI smoke passed. The two ignored startup-gallery GTK tests passed individually, but running both in one process failed because GTK was initialized on different test threads; serial test execution alone does not prevent this harness limitation.
- Live instance, 2026-11-06: the user opened PIC 1.0.3 as a Flatpak with the Demo-2 catalog (85 photos, 6 folders, 8 albums). A read-only photo count took 0.3 ms; the main thread was waiting in the event loop at the time sampled. Startup and navigation tracing were not enabled when that process started, so these observations cannot establish startup, first-photo, or navigation latency. This small catalog is not a large-library benchmark. No restart or catalog changes were made for the observation.
- Latest source via `cargo run --locked`, using an isolated SQLite backup of Demo-2 and isolated XDG directories on tmpfs: in Xvfb/X11 with Cairo, the first launch reached first paint at 546 ms and gallery restoration at 607 ms; a second launch reached them at 492 ms and 533 ms. The catalog held 85 photos and the saved view displayed 6. Database opening took 1 ms and the initial query less than 1 ms at millisecond trace resolution in both runs. These measurements use uncontrolled OS caches and do not establish cold-storage, GPU, full-library, or first-thumbnail performance.
- Browsing regression harness on the latest debug binary with 17 generated photos initially reported 11 passes and 4 failures. The test clicked the folder section header instead of the folder row, leaving All Photos active; correcting the click produced 15 passes and 0 failures. This checks navigation behavior, not latency.
- The lightbox foreground-prefetch promotion unit test passed. It verifies request handling, not the under-100-ms display target.
- The earlier traced browsing run logged repeated texture-cache hits with `navigation_ms=0` at millisecond resolution for small generated JPEGs. That timer begins inside `show_photo` after navigation preparation and ends before the displayed frame is painted, so it is only an internal cache-hit observation, not the requested action-to-display benchmark.
- An attempt to run the viewer GUI suite with lightbox tracing was blocked before interaction: the private accessibility bus failed to start and the GUI driver aborted (status 134). No navigation latency was obtained.
- Cache audit found that both fit-sized and native 1:1 lightbox texture caches ignored source modification time and size even though decode requests included them. Separate GTK regressions reproduced stale reuse in both paths; the cache keys and in-flight result checks now include both fields, and the regressions passed. An existing 1:1 GUI test failed earlier in an Xvfb run because 1:1 did not activate; the focused native-cache regression reproduced the issue independently.
- The isolated `edit-navigation` GUI suite passed 8 checks, including slider reset and neutral detent. Its OpenGL renderer was llvmpipe, so PIC selected CPU fallback; the reported approximately 25 ms fallback stages are not an end-to-end GPU preview measurement and do not satisfy the GPU target.
- Native Vulkan enumeration identifies an AMD Radeon RX 7600, but the automated native GUI harness cannot run here: `ydotool` and `ydotoold` are missing and `/dev/uinput` is root-only. The 41 targeted CPU render tests passed; they do not prove GPU parity or export fidelity.
- GPU timing resume point: use an isolated library and native Wayland session with hardware OpenGL confirmed by `PICASA_TRACE`, warm the same photo and adjustment, then record input and the first frame containing the changed preview. Repeat for common adjustments and report image size, GPU/driver, sample distribution and cache state. The existing editor trace reports render stages, not input-to-painted-frame latency; the Xvfb/Cairo GUI result must not be substituted for this measurement.
- Four scanner refresh tests passed, covering deleted roots, folders and photos, and preservation on mount-device changes. The ignored offline-navigation regression also passed under Xvfb. These checks do not replace real NFS or removable-drive testing.
- Separate Xvfb regressions passed for stale offline-preview completion and reloading an original after reconnect.
- All 48 targeted edit-model tests and both export-metadata tests passed, covering recipe round trips, undo/redo, and orientation-normalized EXIF cases; they do not replace visual or color-profile validation.
- Cache audit: gallery decoded thumbnails default to 64 MiB, lightbox display textures to 256 MiB/32 entries, NEF source frames to 192 MiB, and viewer source bytes to 64 MiB/16 entries. These are separate budgets, not a global memory ceiling; some caches retain a single oversized entry. A new GTK regression confirms the lightbox entry-count limit and least-recently-used eviction. No peak-memory measurement has been made.
- Six thumbnail cache-layout tests passed, including lookup of sharded and legacy flat entries without scanning and orientation handling. They do not measure scrolling responsiveness.
- Targeted tests passed for corrupt-source recovery suppression, scanner worker cancellation propagation, and parallel export cancellation. They do not establish all interruption and recovery scenarios.
