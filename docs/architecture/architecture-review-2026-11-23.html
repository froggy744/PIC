Problem: four callers each work out the target photos, the toggle rule and the follow-up refreshes on their own, and they disagree.

  • Favourite toggle: InfoBar uses ids.len() > 1 || !photo.favorite() (build.rs:4173); the menu uses !favorite_photo.favorite() (photo_actions.rs:578).
  • Rating: the button toggles back to 0 on the same rating (:4229); the digit key does not (:5512).
  • InfoBar favourite re-runs refresh_grid under active filters (:4192); the menu doesn't, and doesn't refresh Properties.
  • Counts: favourite paths use refresh_library_counts; rating paths use update_library_counts.
  • The target rule lightbox visible ? [photo] : selected_photo_ids(Some(id)) is written 3 times (:4168, :4224, :5507).

Solution: one pure module takes (surface, selection, the mark request, active filters) and returns the target set, the new values and a refresh plan; one GTK adapter applies the plan.

locality: one toggle rule leverage: four callers, one interface table tests replace none disagreements become decisions
