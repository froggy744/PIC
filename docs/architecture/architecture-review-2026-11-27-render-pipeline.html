Problem. The chokepoint is a one-liner; every caller that needs tracing, cancellation, RAW aspect correction or library rotation rebuilds the stages around it. Three rotation copies, two RAW aspect fixes, two inline stage orders.

Solution. The render pipeline module owns the whole path from decoded source to finished pixels, with one hook for trace and cancel; callers pass the photo, the purpose and the target size.

  • A new stage lands everywhere at once
  • Viewer and export cannot drift
  • Tests hit one interface
  • Deletes 2 inline copies, 3 rotations, 1 aspect fix

render pipeline knows source → target scale; sharpen, grain, overlays, text use it. Fit preview looks like a shrunk export.

Problem. Sharpen's 1.1 px sigma and the grain are in output pixels, so the same recipe sharpens about 2.5× harder (relative to the photo) in a Fit viewer than in a full-size export, and the editor GPU differs again.

Solution. The pipeline passes a scale to every size-dependent stage; export composites overlays at output size after the resize.

  • What you see is what exports
  • Smaller exports get faster
  • One parity test per stage
Changes what existing edits look like in the viewer and thumbnails. Owner sees before/after screenshots before it merges.

Kept on purpose. Thumbnails and the viewer at Fit use the embedded preview because a sensor develop is too slow for the UI (owner, 2026-11-27). This candidate does not change that.

Problem. The choice "preview or sensor" is made inside the decoder by size and camera brand: Nikon develops from the sensor at 1:1 and export, every other brand exports its embedded preview, the develop is not cancellable, and its 16-bit result is cut to 8 bit before exposure and shadows run.

Solution. A developed-source module answers "pixels for this photo for this purpose": the embedded preview for thumbnails and Fit (as today), the sensor develop for 1:1, editor and export, one cache, cancellable, with the RAW aspect fix inside.

  • UI speed unchanged
  • Export uses the RAW
  • Aspect fix in one place
  • Optional 16-bit hand-off to tone
Owner's library is Nikon D800 NEF, which already exports from the sensor; the other brands are a smaller gain. Measured cost in the NEF benchmark section.

Problem. The GPU kernels are reachable only from a widget, so the viewer re-renders edited photos on the CPU for every size it shows, and export cannot use the GPU at all.

Solution. A second adapter behind the pipeline's seam renders through a widget-free GL context and reads back; chosen per purpose, CPU stays the reference.

  • Viewer matches the editor
  • Seam justified by two adapters
Only after A–C and measured on a release build: GL runs on one thread while export uses 6, tone is ~35% of export time, and encode is not GPU work.

Plan: stages on refactor/render-pipeline

  1. Baseline (done). Export benchmark above. Keep its outputs as the reference for "pixels unchanged" in stages 2 and 4.
  2. Export encode (not a refactor, biggest measured win). JPEG export through TurboJPEG with the same rebuilt EXIF and sRGB ICC; parallel alpha flatten. Output bytes change, so the check is PSNR against the old encoder plus the existing export metadata tests, then the benchmark again.
  3. A · render pipeline module. One stage runner with a trace/cancel observer; lightbox worker and render_for_export call it; one library rotation; RAW aspect fix moved in. Pixels must be byte-identical: benchmark exact_outputs against stage 1, plus edit::render and lightbox tests.
  4. C · tone module. One neutral rule, one GPU-support rule with its reason, constants generated into the GLSL. Gate: the 6 GL parity tests under Xvfb with GSK_RENDERER=gl LIBGL_ALWAYS_SOFTWARE=1, one process each; CPU outputs byte-identical except where an epsilon fix changes a near-zero slider (listed per case).
  5. B · scale-aware render. Capped exports resize before geometry and tone (largest NEF win: ~1.16 s of 3.47 s at 36 MP); sharpen, grain, text and overlays take the source→target scale. User-visible: before/after screenshots of viewer Fit, 1:1 and export for the owner to approve, plus the benchmark's PSNR against today's export.
  6. D · developed source. Embedded preview stays for thumbnails and Fit. One module decides preview vs sensor by purpose; cancellation inside the develop; RAW aspect fix moved in. Decide from measurements on the Work NEFs: half-size develop for capped exports, a 16-bit hand-off to tone, and whether other brands get the sensor develop for export.
  7. E · GPU adapter (only if stages 2-6 leave tone dominant on a release build): widget-free GL context with FBO readback for the viewer first, export second.
  8. F · lightbox invalidation, folded into D or E when they add cancellable viewer work.

Every stage: one commit, STATUS.md updated, merge only on the owner's word. Open owner decisions: release-build benchmark (AGENTS.md forbids --release unless asked), RAW samples, and whether editor-quality.yml's path filter should include src/lightbox/** and src/thumbnail/**.

Top recommendation

A · One render pipeline module

Every later stage (scale-aware effects, the tone module's two adapters, the RAW develop, a GPU adapter) needs one place to plug into; today it would have to be added three times. Do the encoder fix first for JPEG libraries (largest cost at 12 MP, touches none of this); for your NEFs the big win is B, resizing before tone, which needs A.
