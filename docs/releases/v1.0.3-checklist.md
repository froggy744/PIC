# PIC v1.0.3 release checklist

Focus this release on performance, photographic quality, and reliability; defer large features.

## Performance targets

| Operation | Initial target |
| --- | --- |
| Thumbnail scrolling | No sustained frame stalls in normal browsing |
| Cached photo navigation | Under 100 ms where practical |
| Warm Edit Mode preview | Under 250 ms for common GPU adjustments |
| Repeated library opening | Avoid full rescans of unchanged files |

Current evidence: the local scanner enumerates the tree on an authorized scan and skips healthy records with matching modification time and size. The existing matching-fingerprint regression test passes. Scan authorization tests also pass for availability updates, programmatic selection, and debounced watch refreshes. These tests do not measure startup time or prove that every reopening path avoids scanning; the performance target remains open.

Source audit: `scan_with_control` is entered by scan jobs, opens the catalog, reads the indexed fingerprint map once, and then calls `collect_files_filtered`. The local enumerator visits each non-excluded directory and requests name, type, modification time, and size. Healthy records with matching fingerprints and complete catalog metadata skip `read_metadata`; thumbnail checks are only needed for RAW/HEIF records and create work is skipped when the cached preview exists. Reconciliation runs only after complete enumeration and a second availability/device check. This confirms work is scan-time filesystem enumeration, not a full decode/reimport of unchanged files. No timing for a repeated authorized scan on the large catalog was obtained, so no scanner optimization is justified by current evidence.

Library-switch path audit, 2026-11-06: switching to an already registered DB opens the selected SQLite connection, reads folders/albums/counts/settings and the photo rows for the selected view, then replaces the visible model. This path does not invoke `scan_with_control` or enumerate source folders. It only queues network imports already recorded as resumable in that library. In a native Wayland `cargo run` using the isolated 8,756-photo catalog, SQLite open was 6 ms, the initial photo query 29 ms, first window paint 252 ms, and first mapped thumbnail paint 497 ms; scanning was disabled. A second registered copy was added only to the isolated registry, but AT-SPI exposed only the application frame, not the library controls, so a repeated-switch latency sample could not be collected without further GUI automation. Keep the repeated-library timing checkbox open. No source scan or import occurred in this run.

### Startup investigation (2026-11-06)

- Startup selects the registry's current catalog and opens SQLite on the main thread. Window construction reads folders, albums, counts, settings and the initial photo list before presentation. Gallery population starts on idle after presentation; availability checks and thumbnail recovery also run separately. A previously authorized unfinished network import may resume. Library switching opens the selected database and reloads the catalog on the main thread.
- `PIC_STARTUP_TRACE` records startup catalog and photo-query durations, library-switch open/query/completion timings, and per-call summaries for imported-root availability checks. Timing is opt-in and does not alter scan authorization.
- Isolated Xvfb/X11, Cairo, debug-profile binary, AMD Ryzen 5 5600G: a SQLite backup of an existing 8,756-photo catalog (364 folders, 9 albums; 8,745 local paths and 11 network URIs) was placed on `/tmp` (tmpfs), with isolated XDG state. These are process launches with OS caches uncontrolled, not cold-storage measurements; no live library database was opened by PIC. First paint does not prove thumbnails are visible.
- The large catalog contains 6,297 JPEG/JPEG-extension files, 957 PNG, 875 DNG and 621 NEF, plus 6 TIFF/GIF/WebP/SVG files; catalogued source sizes sum to 45.14 GB and dimensions range from 99×48 to 8,160×8,160. The small Demo-2 catalog has 85 JPEG/PNG photos (104 MB total; dimensions 1,376–2,048 pixels). Startup tests load catalog rows only; they do not decode every RAW file.
- First launch: database open 6 ms, initial photo query 28 ms, first paint 583 ms. Gallery population started at 586 ms but had not returned from scheduling when the process was stopped at 12 seconds. The user reports that the initial delay involved unmounted drives; the exact blocking operation remains unconfirmed by these traces.
- Reopening the same isolated catalog: photo query 28 ms, first paint 592 ms, gallery population scheduled in 3 ms and restoration completed at 799 ms. A further run with a fresh thumbnail cache reached first paint at 596 ms and restoration at 759 ms. This does not reproduce the first launch delay; do not infer its cause.
- An additional isolated copy of the same 8,756-photo catalog on local ext4/NVMe, with a fresh thumbnail cache, reached first paint at 582 ms and gallery restoration at 748 ms; its initial photo query took 29 ms. This was Xvfb/Cairo with uncontrolled OS caches and is not a cold-storage measurement. A preceding run was stopped by a timeout that included compilation, so it is not a valid completion-time sample.
- An isolated `cargo run` of the same catalog remapped the six local imported-root paths in the copied database to absent `/run/media/pic-v103-unmounted-*` paths and retained its private NFS URI. This did not touch the live database. On Xvfb/Cairo, PIC reported database open 6 ms, catalog metadata 4 ms, photo query 31 ms, sort 44 ms, window build 118 ms, first paint 247 ms, and gallery restoration 456 ms. The new trace reported seven root availability checks (six absent local paths and one NFS URI): 124 µs total, slowest 67 µs; the later cached pass took 50 µs total, slowest 2 µs. PIC marked six roots unavailable and ran no scan. Ordinary absent paths do not explain the reported long delay; this does not reproduce a stale FUSE/NFS mount that blocks kernel filesystem calls.
- On the original catalog copy, its six local imported roots were mounted in this environment; direct `Path::is_dir` calls took 0.006–0.138 ms. The private NFS root was unavailable and startup deliberately does not probe it on GTK's thread.
- Remaining: reproduce and diagnose the user-reported delay with an actually unmounted or stalled source; measure true cold storage, visible thumbnails, switching libraries, and local disk rather than tmpfs. No NFS mount was available, and the absent-path simulation cannot establish behavior for a stale mount. Obtain before/after measurements if a confirmed bottleneck is fixed. The catalog includes network URIs, so it is not a pure local-source workload.
- Native Wayland real-photo run, 2026-11-06: the isolated 8,756-photo SQLite backup was opened by `cargo run` with scanning disabled, private XDG directories, and a fresh application thumbnail cache. GTK reported `GskVulkanRenderer realized=true`; the host GPU is AMD Radeon RX 7600 (RADV NAVI33). Across 10 starts per cache state, empty PIC thumbnail-cache median first window after-paint was 1,271 ms (p95 1,396 ms, max 1,422 ms), and first mapped real thumbnail after-paint was 1,561 ms (p95 1,752 ms, max 1,766 ms). Warm-cache medians were 288 ms (window) and 414 ms (first thumbnail), with maxima 306 ms and 433 ms. OS page/storage caches were uncontrolled, so “empty” describes only PIC's thumbnail cache, not cold storage. SQLite open was 6–7 ms and initial photo query 28–30 ms; scanning remained disabled.
- Phase trace separated scheduling from paint: on cold runs the window mapped at 237–245 ms, first frame update at 248–260 ms, layout at 276–300 ms, and paint/after-paint at 1,189–1,196 ms. First useful mapped-thumbnail after-paint followed at 1,466 ms in the trace run. The gap is before GTK's first paint; it is not a long paint callback. `perf` and `strace` were unavailable, and the available scheduler sample included first-thumbnail time rather than isolating layout-to-paint CPU use.
- Confirmed startup workload: automatic thumbnail recovery queried all 8,756 catalog records and indexed thumbnail/cache availability. In trace runs this ran alongside the initial gallery workload; it indexed 8,658 ready and 87 offline entries in approximately 234–483 ms. This recovery is required background cache maintenance, but its eager start competes with initial presentation. No filesystem scan was authorized or started.
- Targeted change: defer the existing recovery request until the saved gallery view restoration callback finishes; a 5-second fallback requests it if restoration never completes. The recovery worker, its existing healthy-cache checks, offline handling, and scan authorization are unchanged. A controlled recovery-suppressed run reached first paint at 786 ms, first thumbnail after-paint at 1,001 ms, and gallery restore at 1,051 ms; recovery-enabled baseline trace measured 1,132 ms, 1,397 ms, and 1,531 ms respectively. With the deferral implemented, a fresh isolated run reached paint at 787 ms, first real thumbnail at 999 ms, and restore at 1,047 ms; recovery started at 1,055 ms and indexed the catalog in the background. The observed change is consistent with roughly 345–480 ms earlier first paint and 398–560 ms earlier first thumbnail, but this is a small A/B sample with uncontrolled OS cache state, not a new 10-run comparison. No change to the scanner was made.
- Verification for the targeted deferral: `cargo check --locked` passed, and ignored GTK test `window::startup_gallery_tests::startup_gallery_restores_only_after_cooperative_model_build` passed under Xvfb/Cairo. The real-catalog comparison used only its isolated database/cache and terminated the recovery worker after confirming it had started; the live catalog was not opened or changed.
- Completed startup optimization: the existing automatic thumbnail recovery now waits until saved-view restoration, with a 5-second fallback if restoration has not completed. The recovery implementation and scan authorization are unchanged. The isolated real-photo comparison, current commit, `cargo check --locked`, and GTK restoration regression above provide the verification evidence.
- Remaining environmental startup validation (not blockers for that code change): repeat a controlled before/after series with identical OS-cache conditions if practical; reproduce the original first-launch delay involving potentially stalled/unmounted mounts; measure a true real NFS mount (unavailable here); and capture a profiler sample isolated to layout-to-first-paint. Continue to distinguish window presentation from first useful image display.
